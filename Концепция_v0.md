# Концепция v0 — Auto-Main (1 бот, полный цикл)

Версия: 0.1 · 2026-11-10 · опирается на `КОНСПЕКТ.md`

---

## 1. Цель и границы

**Цель v0:** один бот стабильно проходит полный цикл без участия человека:
зайти → выбрать анархию → `/warp mine` → добыть руду → упаковать в шалкеры →
сбросить на мейн-анархии Stable-боту → вернуться. Плюс автопочинка кирки через `/ah`.

**Не входит в v0:** масштабирование на N ботов, распределение по 84 серверам как
основной режим (заложить контракт), капча-солвер, продажа через `/buyer`.

**Критерий успеха v0:** 3 суток без падений цикла, ноль ручных вмешательств,
измеримый выхлоп (алмазов/час).

## 2. Что уже есть (не переизобретать)

SoulFire 2.10.7 развёрнут на VDS, HTTPS, прокси, инстанс `ft` рабочий.
SDK даёт всё нужное (проверено по proto):

| Задача | RPC |
|---|---|
| Поиск руды в загруженных чанках | `FindBlocks(block_ids[], max_distance, max_count)` |
| Слом блока | `DigBlock(position, cancel)` (только в пределах reach) |
| Ходьба | `GoTo(PathfindGoal)` + поток `PathfindProgress`, `StopPathfinding` |
| Поворот/движение | `SetRotation`, `SetMovementState`, `ResetMovement` |
| События мира | `WatchBotEvents` (`include_block_updates`, `include_chat`, `include_inventory`, `include_players`, `include_lifecycle`) |
| Инвентарь | `GetInventoryState`, `ClickInventorySlot`, `SetHotbarSlot`, `OpenInventory`, `CloseContainer`, `ClickContainerButton`, `SetContainerText` |
| Предметы | `UseItem`, `ReleaseItem`, `InteractBlock` |
| Прочее | `SendChat`/`SendCommand`, `Respawn`, `WaitForChunks`, `AcquireBotControl` |
| Управление ботом | `SetBotsDesiredState`, `RestartBots`, `WatchBotStatuses` |

Вывод: форк движка или mineflayer не нужны.

## 3. Архитектура

```
FunTime ← боты ← SoulFire dedicated (/opt/soulfire, 217.60.33.212)
                        ↑ gRPC-web + токен, HTTPS
             controller (Node/TypeScript, Docker на том же VDS)
                 ├─ config/         (env: URL, токен, инстанс, бот, пороги)
                 ├─ MineDispatcher  (поллер API шахт + планировщик ротации)
                 ├─ BotSupervisor   (FSM, watchdog, реконнект, алерты)
                 ├─ BulldozerMiner  (скан → планирование → DigBlock)
                 ├─ InventoryManager(lock, hotbar, шалкеры)
                 ├─ AuctionBuyer    (/ah search Бутылка опыта + фильтр цены)
                 └─ LootOffloader   (/an302 → /clan home → сброс в воронки)
```

Контроллер — отдельный процесс: SF переживает его падение, контроллер перезапускается
без потери ботов. Токен — только через env/секрет, в git не коммитить.

**Где работает (жёстко зафиксировано):**
- **Рантайм — только на VDS** (`217.60.33.212`), в Docker рядом с SF (`/opt/automain`), `restart: unless-stopped`.
  Локальный ПК — только для написания кода и отладки; ферма от него не зависит.
- Диспетчер (поллер `funtime.me/api/...`) — внутри того же контейнера: прямой выход в интернет,
  никаких CORS/домашних сетей, круглосуточная работа.
- Часы VDS синхронизированы через `systemd-timesyncd` (проверено: `System clock synchronized: yes`),
  поэтому `reset-ms-left` можно пересчитывать локально; всё равно держим периодическую ресинхронизацию
  (каждые 30–60 с) на случай дрейфа и расхождений.

## 4. FSM бота

```
IDLE
 └→ CONNECT ─→ AUTH ─→ SELECT_AN ─→ WAIT_CHUNKS ─→ WARP_MINE
                                                     ↓
                                                  SCAN ⇄ MINE
                                                     ↓ (инвентарь/шалкеры полны или прочность < 25%)
                                                  GO_MAIN (/an302) ─→ GO_HOME (/clan home) ─→ DROP + REPAIR ─→ SELECT_AN
```

**Test mode** (галочка `Test mode` в SF UI или `TEST_MODE=true`): шаги `GO_MAIN`, `GO_HOME`,
`DROP` и `REPAIR` пропускаются, заход завершается при заполненном инвентаре/шалкерях.
Нужен, чтобы отдельно проверить цепочку API → `/anN` → `/warp mine` → добыча → фасовка.

Прерывания:
- `RESET_TP` — **не проектируем**: по решению владельца ресет шахты не отслеживаем, каждый заход
  начинается с телепорта на `/warp mine`. Если телепорт всё же произойдёт — просто уходим в `SCAN`.
- `DEATH` — респавн → `GO_MAIN` (страховка, даже если «невозможно»).
- `DISCONNECT` — реконнект через свой прокси → `SELECT_AN` (цель помним).
- `STALL` — 180 с без слома → принудительный `WARP_MINE` и пересканирование.
- `LOW_DURABILITY` — `< 25%` → `REPAIR`.

## 5. Ядро: добыча 3×3 (Бульдозер II)

### 5.1 Механика
- Бульдозер II ломает **3×3×1** — плоскость, перпендикулярную взгляду. **Подтверждено скриншотами:**
  при взгляде вниз получается шахта 3×3, при взгляде в стену — тоннель шириной 3 и высотой 3.
- Смотрим строго вниз (`pitch = -90`) → ломаем горизонтальное окно 3×3 в текущем слое.
- Один `DigBlock` = 9 блоков. Магнит притягивает дроп сам, ходить за предметами не надо.
- Окно центрируется на сломанном блоке, поэтому центры через 1 блок дают перекрытие (широкий «коридор»),
  а через 3 — стык в стык без потерь.

### 5.2 Сетка и выравнивание
1. Первый скан `FindBlocks` по рудам: `diamond_ore`, `deepslate_diamond_ore`, `gold_ore`,
   `deepslate_gold_ore`, `lapis_ore`, `redstone_ore`, `iron_ore`, `coal_ore` (± deepslate-варианты).
2. Проверить **выравнивание руды по модулю 3** (`x % 3`, `z % 3`). Если окна руды стоят
   на одной сетке — ставим центры ударов ровно по ней: 1 удар = 1 рудное окно.
3. Если сетка не выровнена — центры считаются динамически (см. 5.4).

### 5.3 Базовый проход (когда конкурентов нет)
Два режима, оба с `pitch = -90`:
- **stride = 3** (по умолчанию): центры через 3 блока, стык в стык, 1 удар = 1 окно.
  Оптимально, если руда генерится пятнами 3×3 на одной сетке (на скриншотах лазурит лежит именно пятном 3×3).
- **stride = 1** (аварийный/человекоподобный): перекрывающиеся окна, шире проруб, больше ударов —
  нужно, если сетка руды не выровнена и окна «не попадают».
Спуск на слой ниже — через свой проруб (бота естественно сносит вниз на 1 блок).
Цель — очистить слой за минимальное число ударов (≈ 4410 / 9 ≈ 490 ударов на всю шахту).

### 5.4 Конкурентный режим (на шахте есть люди)
Главное: не «копай всё», а **бей окна с максимальной ценностью на единицу времени**.

- Раз в 250–400 мс пересканировать (`FindBlocks`) и пересчитывать приоритеты.
- Для каждого кандидата-центра `p` считать:
  `value(p) = Σ вес(блок в окне 3×3 горизонтально)` — алмаз 1.0, золото 0.5, мусор 0.
- `cost(p) = путь(p)/скорость + время_удара`.
- Выбор: `argmax value/cost`.
- **Важно**: `block_updates` сообщают, что соседние блоки уже сломаны (нами или другими) →
  вычёркиваем их из карты и пересчитываем мгновенно, без «слепых» ударов в пустоту.
- Люди делят с нами те же кластеры, но бот видит весь кубоид сразу и не тратит время на
  поиск глазами. Преимущество — в скорости перепланирования, а не в силе.
- Игроков игнорируем (PvP-риска нет): не убегаем, не снижаем темп.

### 5.5 Спуск
- Слой Y85 → вычищаем → падаем/шагаем на Y84 в своём прорубе → повтор до Y76.
- Не копать «на себя» без нужды: стоять на уже очищенной кромке, ломать впереди/вниз.
- Если `GoTo` не находит путь — локальный фолбэк: `SetMovementState` + `SetRotation`.

### 5.6 Стоп-условия
- Нет целей с `value > 0` (всё вычищено/забрали другие) → ждать ресет или менять сервер.
- Инвентарь + шалкеры заполнены → `INV_FULL`.
- Прочность < 25% → `LOW_DURABILITY`.
- Бюджет времени на заход исчерпан (`max_run_seconds`) → закрываем заход и берём следующую цель.

## 6. Инвентарь и шалкеры

### 6.1 Раскладка (hotbar)
1 — кирка, 2 — еда, 3 — шалкер, 4 — шалкер, 5 — бутылки опыта (когда есть), 6–9 — локалки.

### 6.2 Inventory Lock
- По 1 алмазу/золоту в каждый свободный слот инвентаря (27 слотов) через split-click.
- Мусор не подбирается вообще → экономия слотов и никаких «забитых булыжником» ситуаций.
- Нюанс: после фасовки в шалкер слоты снова пустеют → локать заново.

### 6.3 Фасовка (проверено: плагин)
1. Взять шалкер в главную руку.
2. `SetRotation(pitch = -90 или +90)` — смотреть в воздух, не на блок.
3. `UseItem` → открывается контейнер (без постановки блока).
4. `ClickInventorySlot` с quick-move для стаков алмазов/золота.
5. `CloseContainer`.

Триггер фасовки: нет места под новый стак ценного, либо пауза (нет целей рядом).

## 7. Починка кирки (Mending)

Модель изменена по решению владельца: `/ah` — забота Stable-бота, фарм-бот только **берёт готовые
бутылки из сундука на базе** и чинится.

- Мониторинг `minecraft:damage` в data-компонентах кирки (не NBT `Damage`).
- Порог `< 25%` → флаг `NEED_REPAIR`; ближайший визит на базу (инвентарь полон — всё равно
  летим домой через `/clan home`) закрывает и отгрузку, и починку.
- На базе: взять из «бутылочного» сундука 2–5 стаков, кирку в off-hand, бутылки в главную руку,
  смотреть вниз, `UseItem` пакетами 50–80 мс до восстановления.
- Вернуть кирку в главную руку, **восстановить Inventory Lock** на опустевшие слоты (см. §6.2).
- Если бутылок на базе нет — `IDLE` + алерт, а не `/ah` самим ботом.

Расчёт расхода: 2031 прочности, Unbreaking V (~1/6 износа) ≈ 12k блоков; Mending = 2 прочности
на 1 XP; бутылка ≈ 3–11 XP (~7). Полная починка ≈ 145 бутылок (~5.5 стаков), от порога 25%
≈ 110 бутылок (~4 стака).

## 8. База: отгрузка через `/clan home`

Важно: клан-хом зарегистрирован **только на одной анархии** — main (например, `/an302`).
С других анархий команда на базу не переносит, поэтому маршрут такой:

```
MINE (anarchy X) ─→ /an302 ─→ /clan home ─→ база (drop + repair) ─→ /anN (следующая цель)
```

- Main-анархия (`base.homeAnarchy`) **исключается из целей фарма автоматически** (`targetPolicy`
  добавляет её в deny) — там стоит хом и база, копать её нельзя.
- Триггер: инвентарь + рабочие шалкеры заполнены (или `NEED_REPAIR`).
- `/clan home` → `WaitForChunks` → `GoTo` точка сброса у воронок → сброс стаков/шалкеров.
- Точку хома, членство ботов в клане и продажу владелец делает вручную — контроллер только ходит
  по готовой точке.
- Возврат: `/anN` по цели диспетчера → `/warp mine` → новый заход.

**Проверить на практике:**
- кулдаун/лимит `/clan home` (не кикает ли за частые телепорты);
- пропускная способность воронок: 2.5 предмета/с → полный шалкер ≈ 11.5 мин на одну воронку;
  либо 4–8 воронок параллельно, либо возить шалкеры целиком и распаковывать на базе.

**Нужно от владельца:** номер main-анархии (подтвердить 302) и координаты воронок относительно точки хома.
Это единственные координаты во всей схеме.

## 9. Диспетчер и ротация (ключевой вывод из API)

Данные: 84 анархии, по одной шахте, таймеры размазаны (медиана ~3.3 мин, от 2 с до 7.5 мин),
редкость: default / mythical / legendary (+ поле следующей редкости).

Отсюда стратегия для одного бота:
1. Поллер раз в 5–10 с, `reset-ms-left` экстраполируем локально.
2. Считаем `eta = reset > now + travel` (travel ≈ переход `/anN` + прогрузка).
3. Целимся в шахту, которая ресетнётся через `travel + 10…20 с` → приезжаем к свежей руде.
4. Приоритет: `legendary` > `mythical` > `default` (проверить экспериментом, что редкость
   реально влияет на алмазы), при равенстве — меньше конкурентов/ближе таймер.
5. Если на текущей шахте руда кончилась раньше ресета — сразу переход на следующую цель,
   не ждать ресета.

Для v0 ротация выключена (фиксированный `/anN`), но интерфейс `getNextTarget()` делаем сразу.

## 12. Риски и ограничения

- Правила FunTime: ферма ботов — риск бана. Изоляция прокси не отменяет риск.
- **Прокси должны быть sticky**: капча приходит только на новом IP/после долгого оффлайна,
  поэтому ротация прокси = ручная капча = остановка фермы.
- Редкость шахт может быть «маркетингом» и не влиять на алмазы — проверить до приоритизации.
- `GoTo` на кромке шахты может вести в яму — нужен свой планировщик шагов по очищенной зоне.
- Обновление образа SF может сломать Via-трансляцию (777/767) — фиксировать тег.

## 13. Форма реализации: внешний SDK-сервис, а не плагин

Рассмотрены три варианта:

| Вариант | Что это | Плюсы | Минусы |
|---|---|---|---|
| InternalPlugin (Java/Fabric) | код внутри процесса SF, как `AutoEat`/`AntiAFK` | прямой доступ к клиенту, свои миксины | Java + Fabric, привязка к версии MC/SF, пересборка при апдейте |
| Визуальные скрипты SF | графы/скрипты внутри SF | быстро для простых циклов | нет HTTP-поллинга, БД, сложного планирования и ротации |
| **Внешний сервис на `@soulfiremc/sdk` (TS)** | отдельный Node-процесс по gRPC-web | всё нужное API уже есть (`findBlocks`, `digBlock`, `goTo`, инвентарь, события), обычный бэкенд-код, не зависит от версии MC | нужен свой процесс и деплой |

**Решение: внешний сервис.** SDK уже даёт полный набор действий (проверено по `sdk/typescript`:
`client.findBlocks`, `tasks.goTo`, `inventory`, `chat`, `behaviors`, `fleet`, `connection`).
Плагин писать только если понадобится вмешательство в сам клиент (миксин/пакеты) — пока не нужно.

Встроенные плагины SF используем как бесплатную подсобку: `AutoEat`, `AntiAFK`, `AutoRegister`,
`ClientBrand`, `DisconnectLogger`.

Состав сервиса:
```
controller/
  src/
    index.ts          — bootstrap, конфиг, DI
    dispatcher.ts     — поллер /plugin/mines, планировщик целей
    runner.ts         — жизненный цикл одного бота (FSM)
    miner.ts          — скан, скоринг, DigBlock
    inventory.ts      — lock, hotbar, шалкеры
    repair.ts         — /ah + бутылки
    offload.ts        — /anMain + сброс
    supervisor.ts     — watchdog, реконнект, алерты
    metrics.ts        — счётчики и лог
  config/            — yaml-профили (см. §15)
  Dockerfile
```

## 14. Приоритет руд и пропуск недостижимых целей

Никакого «зрения»/рендера не нужно: `findBlocks(block_ids, max_distance, max_count)`
возвращает точные координаты руды из уже загруженных чанков.

- Веса руд — конфиг: `diamond: 1.0`, `gold: 0.5`, `lapis: 0.1`, `redstone: 0.1`, `iron: 0`, `coal: 0`.
- Скоринг окна 3×3: `score = Σ вес / (путь + время удара)`.
- Фильтры: только разрешённый `Y`-диапазон шахты, только разрешённые типы блоков.
- **Недостижимая цель** (слишком высоко/нет пути/ETA больше порога): `goTo` вернул `FAILED`
  или прогноз пути > `maxTravelSeconds` → цель помечается `SKIP` на текущую шахту, бот берёт следующую.
- **Бюджет захода**: `maxRunSeconds` на одну шахту (например 240 с). Если цели кончились раньше —
  не стоим: закрываем заход, при необходимости починка/сброс, затем следующая цель диспетчера.

Цикл захода (как ты и описал):
```
spawn → /anN → /warp mine → копка по приоритетам → (починка | сброс на мейн) → ждём ближайший ресет
```

## 15. Конфигурация и переносимость

Всё, что меняется между ботами/анархиями/базами — в YAML, не в коде. Секреты — в `.env`.

```
config/
  bot.yaml        # аккаунт, прокси, пороги, бюджеты
  targets.yaml    # приоритеты серверов/редкостей, allowlist/denylist
  servers.yaml    # профили анархий: warp, кубоид шахты, stash-точки
```

Пример:
```yaml
# servers.yaml
defaults:
  warp: mine
  mine:
    from: { x: 69, y: 76, z: -9 }
    to:   { x: 89, y: 85, z: 11 }
  ore_weights:
    minecraft:diamond_ore: 1.0
    minecraft:deepslate_diamond_ore: 1.0
    minecraft:gold_ore: 0.5
    minecraft:deepslate_gold_ore: 0.5
profiles:
  an205:
    stash: { anarchy: main, x: 0, y: 64, z: 0, receiver: StableBot }
  an311:
    stash: { anarchy: main, x: 120, y: 70, z: -340, receiver: StableBot }
```

- Несколько stash-точек и разные мейн-анархии на профиль → лут не копится в одном месте.
- Hot-reload конфига + валидация схемы (zod) при старте.
- Всё, что «в одном месте» (координаты, аккаунты, точки склада), вынесено в конфиг → перенос на другой
  сервер/аккаунт без правки кода.

Важно: распределение точек склада снижает заметность, но не защищает от логов сервера.
