## 9. Решения по реализации (2026-11-10)

- **Форма:** внешний сервис на TypeScript SDK, НЕ плагин и НЕ визуальный скрипт.
  Причина: SDK покрывает все действия (`findBlocks`, `digBlock`, `goTo`, инвентарь, события),
  а логика требует HTTP-поллинга API, БД, ротации и метрик.
- **Встроенные плагины SF** используются как подсобка: `AutoEat`, `AntiAFK`, `AutoRegister`,
  `ClientBrand`, `DisconnectLogger`.
- **Приоритет руд** — через `findBlocks` (точные координаты), веса в конфиге.
  «Зрение»/рендер не нужны.
- **Недостижимые цели** (высоко/нет пути/долго идти) — помечаем `SKIP`, берём следующую.
- **Цикл захода** вместо «сидеть на одной шахте»: spawn → `/anN` → `/warp mine` → копка →
  починка/сброс → ближайший ресет.
- **Конфигурация** — YAML-профили (bot/targets/servers), секреты в `.env`, hot-reload.
  Несколько stash-точек и разные мейн-анархии на профиль → лут не в одном месте.

Журнал: 2026-11-10 — зафиксированы решения по форме реализации и конфигу (см. `Концепция_v0.md` §13–15).

## 11. Оценка: постоянный фарм и готовность данных (моё мнение)

### 11.1 Вердикт по «непрерывному процессу»
Технически реализуемо и, что важнее, **предсказуемо**: задача детерминированная
(фиксированный кубоид, фиксированный варп, механическое окно 3×3), а SDK даёт точные координаты
блоков вместо «зрения». 84 сервера со сдвинутыми таймерами дают отсутствие простоев.

Правильная модель — **не «вечная сессия», а очередь заходов (runs) с бюджетом**:
```
run = { anarchy, цель, бюджет времени, бюджет прочности, лимит инвентаря }
```
Заход закрывается по любому лимиту, а не по «руда кончилась». Так процесс не зависит от того,
что кто-то другой уже выкопал шахту.

### 11.2 Узкие места по убыванию риска

1. **Капча при реконнекте — НЕ ПРОВЕРЕНО.** Если FunTime требует капчу на каждый вход с нового
   соединения, 24/7 без капча-солвера невозможно. Это блокер №1, проверять первым.
2. **Починка через `/ah`.** Опыт с добычи не идёт, значит цикл зависит от аукциона: цена, наличие
   бутылок, окно подтверждения, лимит переплаты. Если цены улетели или лот кончился — ферма встала.
   Экономически это главная статья расхода.
3. **Логистика лута.** Полный шалкер = 27 стаков; сброс требует Stable-бота на мейне. Если он офлайн
   или координаты не совпали — бот копит в никуда и останавливается. Плюс перелёты съедают время.
4. **Конкуренция.** Выхлоп на шахту нестабилен: нельзя планировать «полный выкуп кубоида».
   Нужны метрики (алмазов/мин) и адаптивный выход, иначе бот будет бить в пустоту.
5. **Пропускная способность.** Переход `/anN` + прогрузка ≈ 10–40 с, а свежая шахта «живёт» минуты.
   На одном боте ротация съест заметную долю времени. Масштаб решается числом ботов, а не тюнингом.

### 11.3 Экономика (чего не хватает для честного ответа)
Нужны три числа, иначе «окупается/нет» — гадание:
- цена бутылки опыта на `/ah` (диапазон, не минимум);
- алмазов на одну свежую шахту (среднее по 10 замерам);
- цена алмаза/золота у `/buyer` и на `/ah`.
Из них считается `coins/hour` и `coins/hour с учётом починки и перелётов`.

### 11.4 Готовность данных для прототипа: **7/10**

Есть (проверено):
- рабочий коннект и версия протокола (767), прокси, SF 2.10.7;
- геометрия шахты и механика 3×3×1 (подтверждено скриншотами);
- контракт API шахт + статистика по 84 серверам;
- карта возможностей SDK (что каким RPC делать);
- поведение при ресете и отсутствие PvP-риска (по словам владельца).

Нет (дёшево получить за 1–2 сессии):
- капча при реконнекте;
- `block_updates` после слома (формат и полнота);
- реальные тайминги перехода `/anN` + прогрузка;
- GUI `/ah` (search, lore с ценой, подтверждение);
- `/anMain` + координаты склада + поведение Stable-бота;
- плотность руды на шахту и выхлоп одного захода.

Вывод: для **вертикального среза** данных достаточно. Для «непрерывного фарма 24/7» не хватает
ровно двух вещей — капчи и экономики.

### 11.5 Как бы я строил первый прототип
1. **Recorder (0.5 дня):** один бот, без копки — только connect → `/anN` → `/warp mine` →
   `findBlocks` → запись в JSONL: позиции, найденные руды, время. Даёт карту и тайминги.
2. **Dig one layer (0.5 дня):** `pitch=-90`, `stride=3`, `DigBlock` по центрам, лог `block_updates`.
   Здесь же закрывается вопрос про 8 соседей.
3. **Full run:** слои 85→76, счётчики `breaks`, `diamonds`, `seconds`.
4. **Inventory + shulker:** lock, фасовка, проверка что мусор не подбирается.
5. **Rotation:** диспетчер, 3 цели, сравнение `timer` vs `round_robin`.
6. **Repair:** `/ah` с лимитом цены (последним — самый хрупкий и дорогой модуль).
7. **Offload:** Stable-бот, полный цикл.

Правило: каждый шаг проверяется метрикой, а не «на глаз». Иначе тюнинг превратится в веру.

## 12. Уточнения владельца (2026-11-10) и следствия

1. **Капча** — только при заходе с нового IP или после долгого оффлайна. Владелец решает вручную,
   API-солвер — позже.
   → Следствие: **прокси обязаны быть sticky** (один IP на аккаунт). Ротация прокси = капча = простой.
2. **Починка** — `/ah` больше не задача фарм-бота. Stable-бот закупает бутылки и держит их в сундуке
   на базе; фарм-бот только берёт и чинится.
   → Следствие: из цикла уходит самый хрупкий модуль (`AuctionBuyer`), экономика изолируется
   от фарма. Остаётся «взять из сундука» = обычный container-flow.
3. **Отгрузка** — без Stable-бота: фарм-бот приходит на мейн-анархию (спавн на базе), кидает лут
   в воронки, дальше сортировка в сундуки. Мейн исключается из целей фарма.
   → Следствие: нужна «карта базы» в конфиге (точка спавна, позиции воронок, сундук с бутылками).
4. **Конкуренция** — по оценке владельца несущественна из-за частых обновлений и 84 анархий.
   → Следствие: оставляем метрики, но не строим сложную антиконкурентную логику в v0.
5. **Пропускная способность** — проверим на практике.

### Новые технические следствия, которые надо учесть в коде

**A. Inventory Lock ломается о расходники.**
Лок = «в каждом слоте лежит хотя бы один алмаз/золото/предмет». Как только стек бутылок
израсходован, слот пустеет → начинает подбираться мусор.
→ Нужен обработчик `inventory`-событий: опустевший слот сразу получает 1 алмаз (split-click).
То же после фасовки в шалкер.

**B. Воронки — медленные.**
2.5 предмета/с на воронку. Полный шалкер (1728 предметов) ≈ 11.5 мин.
→ Варианты: 4–8 воронок параллельно, либо сбрасывать **шалкеры целиком** (1 предмет) и распаковывать
на базе отдельным процессом/ботом. Второй вариант выглядит правильным: фарм-бот не простаивает.

**C. Спавн на базе = точка сброса.**
Раз бот появляется на мейне уже на базе, `GoTo` не нужен — достаточно `SetRotation` + `tossStack`.
Это упрощает отгрузку до 5–10 секунд на визит.

**D. Починка совмещается с отгрузкой.**
Оба события (инвентарь полон, прочность < 25%) ведут на базу → один визит закрывает оба.

## 14. Про «сделать чит-клиент как Baritone» (ответ на вопрос)

Технически — да, и частично уже сделано: SoulFire сам является headless-клиентом на Fabric
с миксинами, грузит сторонние моды (в логах видны viafabricplus, fabric-api и т.д.).
Теоретически в образ можно добавить Baritone (LGPL-3.0) и получить его pathfinding/процессы.

Практически — не нужно:
- pathfinding у нас уже есть (`GoTo` RPC + `PathfindProgress`), дублировать его незачем;
- процессы Baritone (`mine`, `goto`) рассчитаны на обычную кирку «1 блок за удар»
  и не умеют exploить окно 3×3 — то есть на нашей механике они проигрывают простому
  жадному алгоритму из §5.4;
- сборка кастомного образа с модом привязывает нас к версии SF/MC и ломается при апдейте;
- Baritone-подобное поведение (маршруты, цели) проще и дешевле написать в контроллере,
  где уже есть данные о блоках.

Итог: «чит-клиент» у нас уже есть по факту (без рендера, с точными данными и прямыми RPC);
добавлять Baritone — это лишняя зависимость без выигрыша.

## 14. Процесс разработки и расширения (как добавляем функции)

### 14.1 Три уровня вмешательства

| Уровень | Что это | Когда | Цена |
|---|---|---|---|
| **1. Композиция RPC (по умолчанию)** | внешний TS-сервис на `@soulfiremc/sdk` | 95% задач: добыча, инвентарь, чат, события, навигация | SF не трогаем, обновления SF не ломают |
| **2. Плагин = Fabric-мод** (`ExternalPlugin`) | jar в `minecraft/mods` + рестарт | нужен тик-луп, перехват пакетов, свои настройки/команды, прямой доступ к `BotConnection`/`LocalPlayer` | Java 25 + Gradle/Loom, жёсткая привязка к версии SF/MC |
| **3. Форк/патч SF** | свой образ | только если плагина недостаточно | полная поддержка форка |

Проверено: `@soulfiremc/sdk` на npm — **2.10.7**, ровно как наш сервер → версии совпадают.
Внешние плагины грузятся Fabric-загрузчиком из `/soulfire/data/minecraft/mods`
(там уже лежит `managed-mod-2.10.7.jar`). Т.е. плагин ставится без пересборки образа.

### 14.2 Dev-loop контроллера
1. Локально (Windows): Node 22 + TypeScript + `@soulfiremc/sdk@2.10.7`, конфиг на zod, тесты vitest.
2. Запуск против живого SF: `https://217.60.33.212` + токен из env.
3. Тестовый бот и отдельная анархия — эксперименты не мешают боевому циклу.
4. Каждая функция — за фича-флагом в `bot.yaml` (`modules: { miner: true, offload: false }`).
5. Порядок проверки: unit с моками RPC → интеграция на тестовом (10 заходов) → метрики → боевой цикл.
6. Деплой: Docker-образ контроллера на VDS, `restart: unless-stopped`, `docker compose up -d --build`.

### 14.3 Dev-loop плагина (если понадобится)
1. Шаблон `github.com/soulfiremc-com/SoulFirePluginExample`, Java 25, Gradle + Loom.
2. `./gradlew build` → jar.
3. Положить jar в `/soulfire/data/minecraft/mods`, `docker compose restart app`.
4. Проверять на тестовом инстансе; версия плагина привязана к версии SF и MC.
На VDS JDK/Gradle нет — сборка локально или в builder-контейнере.

### 14.4 Как решается «нужна новая функция»
1. Есть ли готовый RPC? (таблица в `Концепция_v0.md` §2)
2. Можно ли скомпоновать из существующих? (пример: открыть контейнер → клики по слотам)
3. Только если нет — плагин.

Примеры маппинга:
- приоритет руд → `findBlocks`;
- сброс в воронку → `tossStack`/`ClickInventorySlot`;
- починка → `SetHotbarSlot` + `UseItem`;
- парсинг кика/чата → `WatchBotEvents(include_chat, include_lifecycle)`.

### 14.5 Ограничения
- Действия требуют владения ботом: `AcquireBotControl`/`RenewBotControl`, иначе конфликт с ручным управлением из GUI.
- Плагин ломается при обновлении SF; контроллер — нет (SDK версионируется).
- Версии фиксируем: digest образа SF + SDK 2.10.7 + протокол 767.

Журнал: 2026-11-11 — зафиксирован процесс разработки (уровни, dev-loop, порядок добавления функций).
